// ── SCIENTIFIC BACKGROUND ────────────────────────────
//
// WHY SENTINEL-1 SAR FOR FLOOD MAPPING?
// ───────────────────────────────────────
// Sentinel-1 carries a C-band (5.405 GHz) Synthetic
// Aperture Radar that actively illuminates Earth's
// surface with microwave pulses. Unlike optical sensors
// (Sentinel-2, Landsat), SAR penetrates cloud cover
// and operates day and night — both essential during
// flood events, which are almost always accompanied by
// persistent cloud and heavy rainfall that completely
// block optical observation.
//
// WHY DOES WATER APPEAR DARK IN SAR?
// ─────────────────────────────────────
// Calm open water is a specular (mirror-like) reflector.
// Radar pulses strike the flat water surface and scatter
// *away* from the satellite antenna rather than back
// toward it. This produces very low backscatter values,
// making flooded areas appear near-black in SAR imagery.
// This is a robust, physically grounded signal that
// underpins most SAR-based flood mapping algorithms.
//
// WHY VH POLARIZATION?
// ──────────────────────
// VH (transmit Vertical, receive Horizontal) is a
// cross-polarization channel sensitive to volume
// scattering from vegetation and surface roughness.
// Over mixed urban-rural landscapes like Embakasi it
// provides stronger contrast between open water (very
// low backscatter) and surrounding land cover (moderate
// backscatter) than the co-polarized VV channel. VH is
// also less dominated by the urban double-bounce effect,
// making it the preferred band for open-water flood
// delineation.
//
// WHY MEDIAN COMPOSITING?
// ─────────────────────────
// With wider temporal windows (11 days before, 12 days
// after), multiple Sentinel-1 passes will overlap the
// study area. Taking the pixel-wise median across all
// acquisitions in a window suppresses transient noise,
// residual speckle outliers, and single-pass artefacts,
// yielding a more stable and representative image of
// surface conditions for that period than any individual
// scene could provide.
//
// URBAN RADAR REFLECTION NOTE
// ─────────────────────────────
// Buildings produce strong double-bounce returns
// (wall + ground interaction) that appear very bright
// in SAR imagery. Flooded streets between buildings may
// still register elevated backscatter due to surrounding
// structures. Always interpret dark pixels in urban
// contexts carefully and cross-reference with ancillary
// data where possible.
//
// =====================================================

// =====================================================
// STEP 3: SAR PREPROCESSING & SPECKLE FILTERING
// =====================================================
// Study Area : Embakasi, Nairobi, Kenya
// Sensor     : Sentinel-1 GRD (VH polarization)
// Continues from: Step 1 (ROI) + Step 2 (composites)
// =====================================================
//
// ── SCIENTIFIC BACKGROUND ────────────────────────────
//
// WHAT IS SAR SPECKLE NOISE?
// ───────────────────────────
// Speckle is a granular, salt-and-pepper noise pattern
// that appears in ALL coherent imaging radar systems,
// including Sentinel-1. It is NOT a sensor malfunction —
// it is an inherent physical phenomenon that arises from
// the coherent (wave-based) nature of radar illumination.
//
// WHY DOES SPECKLE OCCUR?
// ─────────────────────────
// When a radar pulse illuminates a resolution cell
// (pixel footprint on the ground), it interacts with
// many individual scatterers (soil grains, leaves,
// pebbles, roof tiles). The reflected signals from all
// these scatterers combine at the sensor with random
// phase relationships, producing constructive and
// destructive interference. The result is random
// pixel-to-pixel intensity variation even over
// completely homogeneous surfaces — this is speckle.
//
// WHY IS FILTERING IMPORTANT FOR FLOOD MAPPING?
// ───────────────────────────────────────────────
// Raw speckle creates isolated dark pixels over dry
// land (from destructive interference) and isolated
// bright pixels over flooded areas (from constructive
// interference). Without filtering, a simple threshold
// applied to raw SAR imagery will produce thousands
// of false flood detections and missed flood pixels,
// severely degrading map accuracy.
//
// THE SMOOTHING VS. DETAIL TRADEOFF
// ────────────────────────────────────
// Every speckle filter trades spatial resolution for
// radiometric accuracy:
//   • LARGER kernel → more speckle suppressed,
//     but fine features (narrow streets, small water
//     bodies, thin levees) are blurred or lost.
//   • SMALLER kernel → fine features preserved,
//     but more residual speckle remains.
// The optimal kernel size depends on scene content
// and the smallest flood feature that must be resolved.
//
// WHY EXCESSIVE SMOOTHING IS DANGEROUS
// ──────────────────────────────────────
// Over-smoothing blurs the sharp backscatter contrast
// at the boundary between flooded and dry land. This
// causes the flood edge to be mapped inaccurately,
// systematically under- or over-estimating inundated
// area. For emergency response applications this error
// can have direct consequences on resource allocation.
//
// PRESERVING FLOOD BOUNDARIES
// ─────────────────────────────
// An ideal speckle filter is edge-preserving: it
// smooths homogeneous regions heavily while leaving
// sharp transitions (e.g., water/land edge) intact.
// The focal mean implemented below is a reasonable
// starting point; the optional Lee Sigma filter
// below is a stronger edge-preserving alternative.
//
// =====================================================


// =====================================================
// SECTION 3.1 — FILTERING PARAMETERS
// =====================================================
// All tunable parameters are centralised here.
// Adjust KERNEL_RADIUS_M to control the strength of
// speckle suppression vs. spatial detail preservation.

// ── Focal Mean filter settings ──
// Radius in metres. At Sentinel-1 GRD 10 m resolution:
//   50 m  ≈ 5×5 pixel neighbourhood  (light smoothing)
//   100 m ≈ 10×10 neighbourhood      (moderate — default)
//   150 m ≈ 15×15 neighbourhood      (aggressive)
// Start at 50 m and increase only if speckle remains
// problematic after visual inspection.
var KERNEL_RADIUS_M = 50;

// ── Shared SAR visualization stretch (dB) ──
// Carried forward from Step 2 for consistency.
var VIS_MIN = -25;
var VIS_MAX =   0;
var SAR_VIS = { min: VIS_MIN, max: VIS_MAX, bands: ['VH'] };

print('── Step 3 Parameters ─────────────────────');
print('Focal Mean kernel radius (m) :', KERNEL_RADIUS_M);
print('Display stretch [min, max] dB:', VIS_MIN, VIS_MAX);


// =====================================================
// SECTION 3.2 — FOCAL MEAN SPECKLE FILTER (PRIMARY)
// =====================================================
// The focal mean replaces each pixel's value with the
// average of all pixels within a circular neighbourhood.
// It is the simplest, most computationally stable SAR
// smoother available in GEE and is the recommended
// starting filter for production flood workflows.
//
// ee.Kernel.circle() with units:'meters' automatically
// scales the kernel to the native image pixel size,
// making the radius specification resolution-independent
// and safe to use on GEE's multi-resolution pyramid.

// ── Build the circular averaging kernel ──
var focalKernel = ee.Kernel.circle({
  radius : KERNEL_RADIUS_M,
  units  : 'meters',
  normalize: true    // average (not sum) of neighbourhood
});

print('── Focal Mean Kernel ─────────────────────');
print('Kernel object:', focalKernel);


// ── Helper function: apply focal mean to one image ──
// Encapsulating the filter in a function keeps the
// before/after application DRY (Don't Repeat Yourself)
// and makes it trivial to swap in a different filter
// later without changing downstream code.
//
// Parameters:
//   image  — clipped, single-band (VH) ee.Image
//   kernel — ee.Kernel to convolve with
//   roi    — ee.Geometry for final clip
//
// Returns: speckle-filtered ee.Image, clipped to ROI.

var applyFocalMean = function(image, kernel, geometry) {

  var filtered = image
    // .reduceNeighborhood() applies the kernel to each
    // pixel, computing the weighted mean across the
    // circular neighbourhood defined by focalKernel.
    .reduceNeighborhood({
      reducer : ee.Reducer.mean(),
      kernel  : kernel
    })
    // GEE appends '_mean' to the band name after
    // reduceNeighborhood; rename back to 'VH' so all
    // downstream code can reference the band by name
    // without needing to know which filter was applied.
    .rename('VH')
    // Re-clip to ROI: reduceNeighborhood can slightly
    // expand the valid-pixel footprint at image edges.
    .clip(geometry);

  return filtered;
};

// =====================================================
// STEP 4: SAR CHANGE DETECTION
// =====================================================
// Study Area : Embakasi, Nairobi, Kenya
// Sensor     : Sentinel-1 GRD (VH polarization)
// Continues from: Step 3 (beforeFiltered, afterFiltered)
// =====================================================
//
// ── SCIENTIFIC BACKGROUND ────────────────────────────
//
// SAR BACKSCATTER CHANGE PRINCIPLES
// ───────────────────────────────────
// Sentinel-1 measures backscatter intensity — the
// fraction of radar energy reflected back toward the
// satellite. When surface conditions change between
// two acquisition dates, the backscatter value at
// that pixel changes measurably.
//
// In flood mapping:
//   DRY LAND  → moderate-to-high backscatter (soil,
//               vegetation, urban structure scatter)
//   OPEN WATER → very low backscatter (specular
//               reflection away from sensor)
//
// When flooding occurs, previously dry pixels become
// smooth water surfaces. Their backscatter drops
// sharply — often by 5–15 dB. This large, spatially
// coherent decrease is the flood signal we exploit.
//
// WHY USE FILTERED IMAGES FOR CHANGE DETECTION?
// ───────────────────────────────────────────────
// Raw SAR speckle creates random pixel-to-pixel
// variation of ±3–5 dB even over stable surfaces.
// Without prior speckle filtering (Step 3), this
// noise would generate thousands of false "changes"
// across the entire scene. Working with the filtered
// composites (beforeFiltered, afterFiltered) ensures
// that detected changes reflect genuine surface
// transitions rather than noise artefacts.
//
// TEMPORAL CONSISTENCY
// ──────────────────────
// Both images must be from the same relative orbit
// (ascending or descending) and the same instrument
// mode (IW). Using acquisitions from different orbit
// geometries introduces incidence-angle differences
// that create systematic backscatter offsets
// unrelated to flooding — a common error in
// operational workflows. The Step 2 base collection
// filter ensures this consistency.
//
// URBAN SAR FLOOD MAPPING CHALLENGES
// ─────────────────────────────────────
// Embakasi is a dense, mixed urban-informal settlement.
// Urban SAR flood mapping is inherently complex:
//
//   DOUBLE-BOUNCE: Vertical walls + horizontal ground
//   create a dihedral reflector that sends energy
//   directly back to the sensor. Buildings appear
//   very bright and stable. Even flooded streets
//   between buildings may show INCREASED backscatter
//   (wall + water double-bounce) rather than the
//   expected decrease — the opposite of the open-
//   water signal. This means some truly flooded
//   urban pixels will NOT be detected by simple
//   thresholding in Step 5.
//
//   VOLUME SCATTERING: Dense informal structures with
//   varied roof materials produce complex, mixed
//   scattering signatures that are hard to separate
//   from water signals.
//
//   SHADOW & LAYOVER: Tall buildings create radar
//   shadow zones (no return) and layover artefacts
//   that can mimic water darkening.
//
// The change images produced below will appear patchy
// and complex in dense urban zones. This is expected
// and physically meaningful — not a processing error.
//
// =====================================================


// =====================================================
// SECTION 4.1 — CHANGE DETECTION PARAMETERS
// =====================================================
// Centralised parameters for easy adjustment.

// ── Ratio image display range ──
// A ratio of 1.0 means no change (after = before).
// Values < 1.0 indicate backscatter DECREASE (flooding).
// Values > 1.0 indicate backscatter INCREASE (drying,
// urban double-bounce from water between buildings).
// Display range [0, 1] compresses the flood signal
// into the low end of the color ramp.
var RATIO_MIN  = 0;
var RATIO_MAX  = 1;

// ── Difference image display range (dB) ──
// Negative values = backscatter decrease (flooding).
// Positive values = backscatter increase.
// A range of [-10, 10] dB captures most realistic
// change magnitudes without saturating the display.
var DIFF_MIN   = -10;
var DIFF_MAX   =  10;

print('── Step 4 Parameters ─────────────────────');
print('Ratio display range   :', RATIO_MIN, '→', RATIO_MAX);
print('Difference range (dB) :', DIFF_MIN,  '→', DIFF_MAX);


// =====================================================
// SECTION 4.2 — METHOD 1: RATIO-BASED CHANGE DETECTION
// =====================================================
//
// FORMULA:  ratioImage = afterFiltered / beforeFiltered
//
// WHY RATIO?
// ───────────
// Division is a multiplicative normalization: it
// cancels out spatially constant factors such as
// topographic slope effects, stable vegetation
// biomass, and sensor calibration offsets that are
// common to both images.
//
// Because SAR backscatter values are stored in
// linear power units in GEE's S1_GRD collection,
// division produces a dimensionless ratio where:
//
//   ratio ≈ 1.0  → no change (stable surface)
//   ratio << 1.0 → strong decrease (flooded candidate)
//   ratio >> 1.0 → strong increase (urban double-
//                  bounce, newly exposed rough surface)
//
// The ratio method is generally preferred over the
// difference method when images have slightly
// different noise levels, because noise divides out
// rather than accumulating additively.
//
// LIMITATION: If beforeFiltered contains very low
// values (near-zero pixels over permanent water),
// division can produce extremely large or unstable
// ratio values. A small constant can be added to
// the denominator if needed in future steps.

var ratioImage = afterFiltered
  .divide(beforeFiltered)
  .rename('ratio')
  .clip(roi);

print('── Ratio Image Diagnostics ───────────────');
print('ratioImage object     :', ratioImage);
print('ratioImage band names :', ratioImage.bandNames());
print('ratioImage projection :', ratioImage.projection());


// =====================================================
// SECTION 4.3 — METHOD 2: DIFFERENCE-BASED CHANGE
// =====================================================
//
// FORMULA:  differenceImage = afterFiltered - beforeFiltered
//
// WHY DIFFERENCE?
// ─────────────────
// Subtraction in dB-equivalent linear space gives
// an absolute change value whose sign directly
// indicates direction:
//
//   difference ≈  0   → stable surface
//   difference <  0   → backscatter DECREASE
//                        (flood candidate — smooth
//                         water replacing rough land)
//   difference >  0   → backscatter INCREASE
//                        (urban double-bounce from
//                         water, newly rough surfaces)
//
// The difference method is more intuitive to
// interpret visually and is widely used in published
// SAR flood mapping literature. However, it can be
// sensitive to additive noise and systematic offsets
// between the two images (e.g., different soil
// moisture conditions unrelated to flooding).
//
// COMPLEMENTARY USE:
// Using BOTH ratio and difference images allows
// cross-validation of flood signals. A pixel flagged
// as flooded by BOTH methods is a much stronger
// candidate than one detected by only one method.
// This dual-evidence approach underpins the Step 5
// thresholding strategy.

var differenceImage = afterFiltered
  .subtract(beforeFiltered)
  .rename('difference')
  .clip(roi);

print('── Difference Image Diagnostics ──────────');
print('differenceImage object     :', differenceImage);
print('differenceImage band names :', differenceImage.bandNames());
print('differenceImage projection :', differenceImage.projection());

//   Deep red   → strong increase (urban double-bounce)

// STEP 5 (CORRECTED): THRESHOLD-BASED FLOOD EXTRACTION

// Fix applied: CATEGORY D — Threshold + Logic Failure
// Changes made:
//   [FIX 1] Ratio threshold relaxed:      0.70 → 0.85

//   [FIX 4] floodMaskFinal cast to Byte
//            before .selfMask() to guarantee
//            binary integer rendering in GEE
// =====================================================
//
// WHY THESE FIXES ARE SCIENTIFICALLY JUSTIFIED
// ─────────────────────────────────────────────
// Standard rural SAR flood thresholds (ratio < 0.7,
// diff < -3 dB) assume open, flat terrain where
// floodwater creates a clean specular surface. In
// Embakasi's dense urban fabric:
//
//   • Buildings create double-bounce returns that
//     partially OFFSET the water darkening signal,
//     producing a weaker net backscatter decrease.
//
//   • Flooded streets between structures can increase
//     backscatter (wall-water dihedral), meaning the
//     signal reaches neither ratio < 0.7 NOR diff < -3.
//
//   • Informal roofing materials (iron sheets, plastic)
//     produce highly variable pre-event backscatter,
//     compressing the dynamic range of the change signal.
//
// Relaxing to ratio < 0.85 and diff < -1 dB is
// consistent with published urban SAR flood mapping
// studies (Twele et al. 2016, Chini et al. 2019).
//
// OR logic is preferred at this stage because it is
// better to over-detect and refine in Step 6 (slope
// masking, permanent water removal) than to under-

// =====================================================


// =====================================================
// SECTION 5.1 — THRESHOLD PARAMETERS (CORRECTED)
// =====================================================

// FIX 1: Relaxed ratio threshold for urban environment
// Original: 0.70 — too strict for Embakasi urban fabric
// Corrected: 0.85 — captures attenuated urban flood signal
// Scientific basis: a 15% backscatter reduction (ratio=0.85)
// corresponds to ~1.4 dB decrease — detectable above

var RATIO_THRESHOLD = 0.85;  // FIX 1: was 0.70

// FIX 2: Relaxed difference threshold for urban environment
// Original: -3 dB — misses weak urban flood signals
// Corrected: -1 dB — captures minimal but genuine decreases
// Scientific basis: post-filtering speckle standard deviation
// in Sentinel-1 GRD VH is ~0.5–1.0 dB; a -1 dB threshold
// sits at the edge of detectable change above noise floor.
var DIFF_THRESHOLD  = -1;    // FIX 2: was -3

// FIX 3: Switch from AND to OR combination
// Original: 'AND' — both methods must agree simultaneously
// Corrected: 'OR' — either method is sufficient
// Scientific basis: in urban SAR the ratio and difference
// methods are sensitive to slightly different aspects of
// the backscatter change. OR captures the union of both
// signals and is appropriate for first-pass flood extent
// before mask refinement steps.
var COMBINATION_METHOD = 'OR';  // FIX 3: was 'AND'

// =====================================================
// STEP 6: FLOOD MASK REFINEMENT
// =====================================================
// Study Area : Embakasi, Nairobi, Kenya
// Input      : floodMaskFinal (from Step 5)
// Output     : floodMaskRefined
// Continues from: Step 5 (floodMaskFinal exists)
// =====================================================
//
// WHY REFINEMENT IS NECESSARY
// ─────────────────────────────
// The Step 5 flood mask is a first-pass product based
// purely on SAR backscatter change. It contains three
// well-documented categories of false positives:
//
//   1. PERMANENT WATER BODIES (rivers, seasonal ponds)
//      These appear dark in SAR year-round. They were
//      dark BEFORE the flood event and dark AFTER it,
//      so the change signal is weak — but relaxed
//      thresholds (Step 5 Fix) may still flag them.
//      More importantly, they are NOT flood-induced
//      inundation and must be excluded from the map.
//
//   2. STEEP TERRAIN (slopes, embankments, cuttings)
//      Radar look-angle effects cause steep slopes
//      to return anomalously low backscatter (radar
//      shadow, foreshortening). This mimics the water
//      darkening signal and creates false positives
//      on any slope steeper than ~5°. Embakasi has
//      gentle terrain overall but contains drainage
//      channel embankments that must be excluded.
//
//   3. ISOLATED NOISE PIXELS (speckle residuals)
//      Even after focal mean filtering, residual
//      speckle creates single isolated pixels or
//      tiny 2–3 pixel clusters that pass the flood
//      threshold by chance. These are statistically
//      indistinguishable from real floods at the
//      pixel level but have no spatial coherence.
//      Morphological cleaning removes them by
//      requiring flood pixels to belong to a
//      connected cluster of minimum size.
//
// =====================================================


// =====================================================
// SECTION 6.0 — REFINEMENT PARAMETERS
// =====================================================
// All tunable values centralised here for easy
// adjustment without editing the code body.

// ── JRC permanent water threshold ──
// Pixels with water occurrence > this value (%) across
// the full JRC 1984–present record are treated as
// permanent water and excluded from the flood mask.
// 90% = present in 9 out of 10 observed years.
// Lower this (e.g. 50%) to also remove seasonal water.
var JRC_OCCURRENCE_THRESHOLD = 90;

// ── Slope threshold (degrees) ──
// Pixels steeper than this angle are excluded.
// 5° is the widely adopted threshold in SAR flood
// mapping literature (Horritt et al. 2001, Twele 2016).
// For very flat urban areas like Embakasi, 3° may be
// more appropriate — increase if too many valid pixels
// are removed.
var SLOPE_THRESHOLD_DEG = 5;

// ── Minimum connected flood cluster size (pixels) ──
// Isolated clusters smaller than this number of
// connected pixels are classified as noise and removed.
// At 10 m resolution: 8 pixels ≈ 800 m² ≈ 0.08 ha.
// Increase to 20–50 if the map still appears noisy.
// Decrease to 4 if small genuine flood pools are missed.
var MIN_CONNECTED_PIXELS = 8;

// ── Connectivity for morphological cleaning ──
// 4  = cardinal neighbours only (more conservative)
// 8  = cardinal + diagonal neighbours (more inclusive)
var CONNECTIVITY = 8;

print('── Step 6 Refinement Parameters ──────────');
print('JRC occurrence threshold (%)  :', JRC_OCCURRENCE_THRESHOLD);
print('Slope threshold (degrees)     :', SLOPE_THRESHOLD_DEG);
print('Min connected pixels          :', MIN_CONNECTED_PIXELS);
print('Connectivity                  :', CONNECTIVITY);


// =====================================================
// SECTION 6.PRE — BASELINE PIXEL COUNT
// =====================================================
// Record the original Step 5 flood mask statistics
// BEFORE any refinement so we can compare before/after.

var originalCount = floodMaskFinal
  .reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });

var originalPixels = ee.Number(
  originalCount.get('flood_final'));

var originalAreaKm2 = originalPixels
  .multiply(100)    // 10m × 10m = 100 m² per pixel
  .divide(1e6);     // m² → km²

print('── Baseline (Pre-Refinement) ──────────────');
print('Original flood pixel count :', originalPixels);
print('Original flood area (km²)  :', originalAreaKm2);


// =====================================================
// STEP 6A: REMOVE PERMANENT WATER
// =====================================================
//
// DATASET: JRC Global Surface Water (Landsat-derived)
// Collection: JRC/GSW1_4/GlobalSurfaceWater
// Band used : 'occurrence' — percentage of time a
//             pixel was observed as water over the
//             entire 1984–present record.
//
// WHY JRC OCCURRENCE?
// ────────────────────
// The JRC occurrence layer is the most reliable global
// indicator of permanent and semi-permanent water. A
// pixel with occurrence > 90% has been classified as
// water in more than 90% of all valid Landsat
// observations — it is structurally water, not flood.
//
// WHY NOT USE THE SAR IMAGE ITSELF TO MASK WATER?
// ────────────────────────────────────────────────
// Using the before-event SAR image to exclude "already
// dark" pixels creates a circular dependency and would
// miss water bodies that were partially filled during
// the before period. The independent optical-based JRC
// record avoids this problem entirely.
//
// IMPLEMENTATION NOTE:
// We create a binary permanent-water mask (1 = perm
// water, 0 = not) then SUBTRACT it from the flood mask.
// Pixels that are permanent water become 0 (not flood).

print('── STEP 6A: Permanent Water Removal ───────');

// Load JRC Global Surface Water occurrence band
var jrcGSW = ee.Image('JRC/GSW1_4/GlobalSurfaceWater')
  .select('occurrence');

// Create permanent water mask
// 1 = permanent water (to be removed from flood mask)
// 0 = not permanent water (keep flood detection)
var permanentWaterMask = jrcGSW
  .gte(JRC_OCCURRENCE_THRESHOLD)  // 1 where occurrence ≥ 90%
  .unmask(0)       // pixels with no JRC data → treat as not-water
                   // (important over urban areas with data gaps)
  .clip(roi);

// Apply: remove permanent water from flood mask
// .where(condition, newValue):
//   where permanentWaterMask = 1 (permanent water),
//   set flood pixel to 0 (not a new flood)
var floodMaskNoPermWater = floodMaskFinal
  .where(permanentWaterMask.eq(1), 0)
  .toByte()
  .rename('flood_final')
  .clip(roi);

// Pixel count after Step 6A
var countAfter6A = floodMaskNoPermWater
  .reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });
print('Permanent water pixels removed :',
      originalPixels.subtract(
        ee.Number(countAfter6A.get('flood_final'))));
print('Flood pixels after 6A          :',
      countAfter6A.get('flood_final'));

// Visualize JRC permanent water layer for reference
Map.addLayer(
  permanentWaterMask.selfMask(),
  { min: 0, max: 1, palette: ['00BFFF'] },
  '6A REF | JRC Permanent Water (> ' +
    JRC_OCCURRENCE_THRESHOLD + '% occurrence)',
  false    // hidden by default
);


// =====================================================
// STEP 6B: APPLY SLOPE MASK
// =====================================================
//
// DATASET: SRTM Digital Elevation Model (30 m)
// Collection: USGS/SRTMGL1_003
//
// WHY SLOPE MATTERS FOR SAR FLOOD MAPPING?
// ──────────────────────────────────────────
// SAR backscatter is highly sensitive to surface
// geometry relative to the radar look direction:
//
//   FORESHORTENING: Slopes facing the sensor compress
//   spatially and return anomalously high backscatter.
//
//   RADAR SHADOW: Slopes facing away from the sensor
//   receive no illumination and return near-zero
//   backscatter — indistinguishable from open water.
//
// Both effects create false positive flood detections
// on slopes. The standard mitigation is to exclude
// all pixels steeper than SLOPE_THRESHOLD_DEG.
//
// WHY 5 DEGREES?
// ───────────────
// At Sentinel-1 IW incidence angles (30°–46°), slope
// effects become significant above ~5°. Below 5° the
// terrain contribution to backscatter variation is
// smaller than the speckle noise floor — safe to ignore.
// Embakasi is largely flat but drainage embankments
// and the Nairobi River valley walls exceed 5°.

print('── STEP 6B: Slope Mask Application ────────');

// Load SRTM DEM and compute terrain slope
var srtmDEM = ee.Image('USGS/SRTMGL1_003');
var slope   = ee.Terrain.slope(srtmDEM);   // output in degrees

// Create valid-terrain mask
// 1 = acceptable slope (keep) — slope BELOW threshold
// 0 = too steep (remove from flood mask)
var slopeMask = slope
  .lt(SLOPE_THRESHOLD_DEG)   // 1 where slope < 5°
  .clip(roi);

// Apply: multiply by slope mask
// Flood pixels on steep terrain become 0 (excluded).
// Flood pixels on flat terrain remain unchanged.
var floodMaskNoSlope = floodMaskNoPermWater
  .multiply(slopeMask)        // 1×1=flood kept, 1×0=removed
  .toByte()
  .rename('flood_final')
  .clip(roi);

// Pixel count after Step 6B
var countAfter6B = floodMaskNoSlope
  .reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });
print('Slope-related pixels removed   :',
      ee.Number(countAfter6A.get('flood_final'))
        .subtract(ee.Number(countAfter6B.get('flood_final'))));
print('Flood pixels after 6B          :',
      countAfter6B.get('flood_final'));

// Visualize slope layer for reference
Map.addLayer(
  slope.clip(roi),
  { min: 0, max: 15, palette: ['white','yellow','orange','red'] },
  '6B REF | SRTM Slope (degrees)',
  false    // hidden by default
);

Map.addLayer(
  slopeMask.not().selfMask().clip(roi),  // show EXCLUDED steep areas
  { min: 0, max: 1, palette: ['FF4500'] },
  '6B REF | Excluded Steep Pixels (slope > ' +
    SLOPE_THRESHOLD_DEG + '°)',
  false
);


// =====================================================
// STEP 6C: MORPHOLOGICAL CLEANING
// =====================================================
//
// WHY MORPHOLOGICAL CLEANING?
// ────────────────────────────
// After Steps 6A and 6B, some single-pixel or
// small-cluster false positives remain. These arise
// from:
//   • Residual speckle that survived focal mean filtering
//   • Isolated surface roughness changes (construction,
//     vegetation trampling, vehicle tracks)
//   • Sub-pixel permanent water not captured by the
//     coarser JRC 30 m record
//
// Real flood inundation is spatially contiguous: water
// fills connected low-lying areas and spreads along
// drainage paths. An isolated cluster of 2–3 pixels
// surrounded by dry land is almost certainly noise.
//
// HOW connectedPixelCount WORKS:
// ───────────────────────────────
// For each flood pixel, GEE counts how many spatially
// connected flood pixels share the same value (1) in
// its neighbourhood, using the specified connectivity.
// The result is an image where each flood pixel's value
// equals the size of its connected cluster.
// Pixels belonging to clusters SMALLER than
// MIN_CONNECTED_PIXELS are then set to 0 (removed).
//
// CONNECTIVITY = 8 (default here)
// Considers all 8 neighbours (cardinal + diagonal).
// This joins clusters connected diagonally, which is
// appropriate for flooded drainage paths that often
// run diagonally relative to the pixel grid.

print('── STEP 6C: Morphological Cleaning ────────');

// Step 1: Count connected flood pixels per cluster
// Input must be a binary image (0/1) — floodMaskNoSlope
// already satisfies this requirement.
var connectedCount = floodMaskNoSlope
  .connectedPixelCount({
    maxSize     : 1024,       // max cluster size to evaluate
                              // set high to avoid truncation
    eightConnected: (CONNECTIVITY === 8)
  });

// Step 2: Create minimum-size filter mask
// 1 = pixel belongs to a cluster large enough to keep
// 0 = pixel belongs to a tiny cluster → noise → remove
var clusterSizeMask = connectedCount
  .gte(MIN_CONNECTED_PIXELS);

// Step 3: Apply cluster filter to flood mask
var floodMaskCleaned = floodMaskNoSlope
  .multiply(clusterSizeMask)  // remove small clusters
  .toByte()
  .rename('flood_final')
  .clip(roi);

// Pixel count after Step 6C
var countAfter6C = floodMaskCleaned
  .reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });
print('Noise pixels removed (6C)      :',
      ee.Number(countAfter6B.get('flood_final'))
        .subtract(ee.Number(countAfter6C.get('flood_final'))));
print('Flood pixels after 6C          :',
      countAfter6C.get('flood_final'));

// Visualize removed noise pixels for inspection
var noisePixels = floodMaskNoSlope
  .subtract(floodMaskCleaned)
  .toByte()
  .selfMask()
  .clip(roi);

Map.addLayer(
  noisePixels,
  { min: 0, max: 1, palette: ['FF00FF'] },
  '6C REF | Removed Noise Pixels (magenta)',
  false
);


// =====================================================
// SECTION 6.FINAL — ASSIGN REFINED MASK
// =====================================================
// floodMaskRefined is the clean, science-ready product
// after all three refinement steps. This variable is
// passed to Step 7 (flood statistics and reporting).

var floodMaskRefined = floodMaskCleaned
  .rename('flood_refined')
  .clip(roi);

// Final pixel count and area
var refinedCount = floodMaskRefined
  .reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });

var refinedPixels = ee.Number(
  refinedCount.get('flood_refined'));

var refinedAreaKm2 = refinedPixels
  .multiply(100)
  .divide(1e6);

// Pixels removed by refinement (total noise + artefacts)
var pixelsRemoved = originalPixels.subtract(refinedPixels);
var areaRemovedKm2 = pixelsRemoved.multiply(100).divide(1e6);
var retentionPct = refinedPixels
  .divide(originalPixels)
  .multiply(100);


// =====================================================
// SECTION 6.VIS — MAP VISUALIZATION
// =====================================================

var sarVis      = { min: -25, max: 0, bands: ['VH'] };
var floodVisOld = { min: 0, max: 1, palette: ['0000FF'] };
var floodVisNew = { min: 0, max: 1, palette: ['00CCFF'] };

// ── SAR background ──
Map.addLayer(
  afterFiltered,
  sarVis,
  'REF | Filtered After Flood SAR | VH',
  true
);

// ── Original Step 5 flood mask (OFF by default) ──
// Enable to compare against refined output side-by-side
Map.addLayer(
  floodMaskFinal.selfMask(),
  floodVisOld,
  'Step 5 | Original Flood Mask (unrefined, blue)',
  false    // OFF — enable for before/after comparison
);

// ── Refined flood mask (ON — primary product) ──
Map.addLayer(
  floodMaskRefined.selfMask(),
  floodVisNew,
  'Step 6 | REFINED Flood Mask | Embakasi',
  true
);

Map.centerObject(roi, 11);


// =====================================================
// SECTION 6.SUMMARY — DIAGNOSTIC PRINT
// =====================================================

print('════════════════════════════════════════════');
print('STEP 6 COMPLETE — Refinement Summary');
print('════════════════════════════════════════════');
print('── Before Refinement ───────────────────────');
print('Original pixel count  :', originalPixels);
print('Original area (km²)   :', originalAreaKm2);
print('── After Each Stage ────────────────────────');
print('After 6A (perm water) :', countAfter6A.get('flood_final'));
print('After 6B (slope mask) :', countAfter6B.get('flood_final'));
print('After 6C (morphology) :', countAfter6C.get('flood_final'));
print('── Final Refined Output ────────────────────');
print('Refined pixel count   :', refinedPixels);
print('Refined area (km²)    :', refinedAreaKm2);
print('Pixels removed total  :', pixelsRemoved);
print('Area removed (km²)    :', areaRemovedKm2);
print('Mask retention (%)    :', retentionPct);
print('────────────────────────────────────────────');
print('Output variable       : floodMaskRefined');
print('Next step             : Step 7 — Statistics,');
print('                        area calculation &');
print('                        export for reporting');

// ── Helper: safe min/max inspector ──
// reduceRegion can time-out on large ROIs at full
// resolution. scale:100 gives a fast approximate
// result sufficient for debugging — not for final
// analysis. If it still times out, increase to 500.
var DEBUG_SCALE = 100;  // metres — increase to 500 if timeout

var safeMinMax = function(image, bandName, label) {
  var stats = image.select(bandName).reduceRegion({
    reducer  : ee.Reducer.min().combine(
                 ee.Reducer.max(), '', true),
    geometry : roi,
    scale    : DEBUG_SCALE,
    maxPixels: 1e9,
    bestEffort: true   // prevents timeout by auto-scaling
  });
  print(label + ' [min, max]:', stats);
};

var safePixelCount = function(image, bandName, label) {
  var count = image.select(bandName).reduceRegion({
    reducer  : ee.Reducer.sum(),
    geometry : roi,
    scale    : 10,
    maxPixels: 1e9,
    bestEffort: true
  });
  print(label + ' pixel count (sum of 1s):', count);
};
